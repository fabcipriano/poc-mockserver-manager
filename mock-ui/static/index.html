Help

What each request matcher does, and how mocking works in this tool.

The catch-all rule

This environment seeds one forwarding rule that sends every unmocked request through to the real backend. It is never shown in the mocks list, and cannot be edited or deleted through this web interface - it's what makes pass-through work for anything you haven't mocked.

Method and path

Every mock matches on HTTP method and path at minimum - these are the only two fields required to create a mock. Everything below is optional and narrows matching further.

Path parameters

Write a named segment directly in the path using curly braces, e.g. /booking/{id}, then constrain what values that segment may take. A mock on /booking/{id} with id=123 matches requests to /booking/123 but not /booking/456.

Query string parameters

Constrain the mock to requests that include a specific ?name=value pair. A request missing that parameter, or with a different value, will not match and falls through to the real backend (or another mock).

Headers

Constrain the mock to requests that include a specific header value, e.g. X-Test: yes. Useful for mocking only requests from a particular client or test run.

Cookies

Constrain the mock to requests that include a specific cookie value, e.g. session=abc. Handy for mocking behavior tied to a particular session.

Request body (JSON)

Constrain the mock to requests whose JSON body matches what you specify. Choose "Contains at least these fields" to match any request body that includes the fields you listed (extra fields are ignored), or "Exact match" to require the request body to be exactly what you specified, with nothing extra.
