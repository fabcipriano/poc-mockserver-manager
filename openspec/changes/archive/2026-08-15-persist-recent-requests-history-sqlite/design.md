## Context

See `proposal.md` - Why, and `docs/studies/2026-08-09-recent-requests-resilience.md` for the prior investigation this builds on (not repeated here): the shared-poller fix already landed in `2026-08-09-improve-recent-requests-resilience`, so this change does not touch the `O(tabs)` concurrency problem, only what the poller does with each tick's result. Today `Target.history_snapshot` (`mock-ui/app.py`) is replaced wholesale from MockServer's `/mockserver/retrieve` response every `REQUEST_STREAM_POLL_SECONDS`; nothing survives past the next tick, and MockServer's own log is a `maxLogEntries` ring buffer that silently evicts its oldest entries. Multi-target support (`MOCKSERVER_TARGETS` / the `Target` class) already exists and must be preserved.

## Goals / Non-Goals

**Goals:**
- Every request `mock-ui` has observed for a target stays visible on the Recent Requests page until it ages out of `mock-ui`'s own retention policy, regardless of what MockServer itself still retains - i.e. a reliable log for the lifetime of a running `mock-ui` process.
- Reads (`/api/requests` pagination/filters, `/api/requests/stream` live tail) stay correct under the existing multi-target, multi-viewer model.

**Non-Goals** (carried from proposal.md's Impact/Out of scope):
- Reducing the per-tick cost of fetching MockServer's full current log - MockServer's `/mockserver/retrieve` has no cursor/time-range parameter, so every tick still fetches and parses everything MockServer currently holds, same as today.
- Changing MockServer's own `maxLogEntries` or retention behavior.
- Moving off Flask's dev server.
- Persisting history across a `mock-ui` process restart or pod reschedule. The SQLite store lives on local/ephemeral storage; a restart starts each target's history empty, same as today's in-memory behavior. Only in-process reliability (no longer silently losing entries MockServer has already evicted) is in scope, not durability across restarts.

## Decisions

- **Storage: one SQLite file per configured `Target`, at a path derived from the target's `id`.** Rejected a single shared file with a `target_id` column: `Target`s are already independently configured, independently polled (one thread each), and this change adds independent per-target retention pruning - one file per target keeps failure, locking, and pruning fully isolated between targets (a corrupt/full-disk file for one target can't affect another), at the cost of N small files instead of one - acceptable given target counts are small (single digits, per `MOCKSERVER_TARGETS`).
- **Poller changes from "replace snapshot" to "upsert into SQLite."** `_poll_history_once` still does one full `/mockserver/retrieve` fetch per tick (unchanged - see Non-Goals), but instead of `target.history_snapshot = built`, it upserts each fetched entry into that target's SQLite table via `INSERT OR IGNORE`, keyed on a dedup key (next decision). This is what makes previously-observed-but-now-MockServer-evicted entries stay visible: once a row is in SQLite, a later poll tick no longer returning that entry from MockServer does not remove it.
- **Dedup key: `(timestamp, method, path, response_status_code)` as a `UNIQUE` constraint, not a synthetic hash.** MockServer assigns no stable per-request id (same limitation the existing pagination cursor already documents and accepts). This tuple is what the UI already treats as an entry's identity for display purposes; two genuinely distinct requests colliding on all four fields within the same logged millisecond is the same accepted, documented edge case pagination already lives with today - not newly introduced by this change. Alternative considered: hashing the full request+response body too, rejected as adding complexity without closing the underlying gap (MockServer still doesn't give us a real id to key on), and it would make the same "identical retry" case invisible for a different, worse reason (a genuine identical retry would also collide and get silently dropped either way).
- **Ordering/pagination cursor moves from `timestamp` string comparison to SQLite `rowid`.** Persisted storage makes a real monotonic, collision-free ordering key free (`INTEGER PRIMARY KEY` autoincrement), which directly resolves the same-millisecond tie-break `timestamp`-cursor pagination had to document as a known limitation. `list_requests` and the SSE stream's "entries newer than last seen" query both switch to `rowid`-based comparison; the API's cursor value itself can stay opaque to the client (still an opaque `before` token), just backed by `rowid` instead of `timestamp` internally.
- **Live tail reads newly-inserted rows from SQLite each tick, not a separate in-memory buffer.** Considered keeping a small in-memory "just inserted this tick" list alongside the SQLite write to avoid a query per tick; rejected because it reintroduces exactly the kind of transient duplicate state this change is trying to get away from, and a single indexed `SELECT ... WHERE rowid > ?` per target per tick (not per viewer - the poller still runs once per target regardless of viewer count, per the existing shared-poller design) is cheap enough not to justify the extra state.
- **Retention: fixed row cap per target, pruned at the end of each poll tick.** Chosen over TTL because it gives a predictable, easy-to-reason-about disk footprint (`row cap × average row size`) independent of traffic rate, whereas a TTL's disk usage scales with however bursty traffic happens to be. Default cap: 120,000 rows per target (comfortably above the `REQUEST_HISTORY_LIMIT` default of 40 and the page-size of 100, and - unlike an earlier 50,000 draft of this default, corrected after directly re-running the reproduced load-test scenario against the real upsert/prune logic - large enough that the reproduced bug's exact scenario, `scripts/load-test-recent-requests.sh`'s 100,000 distinct `/booking/N` requests followed by a `/booking/20123` lookup, no longer loses the target entry at default settings; a cap below the load test's own request count would let `mock-ui`'s *own* retention re-introduce the same class of loss the persisted store was built to fix), configurable via an env var following this codebase's existing `_parse_positive_int_env` pattern (e.g. `REQUEST_HISTORY_RETENTION_ROWS`). Pruning deletes the oldest rows by `rowid` past the cap, in the same transaction as that tick's upserts.
- **`_detect_history_reset` keeps its purpose but changes what it compares against.** It currently exists to notice when MockServer's own log has been wiped (e.g. MockServer restarted) so the SSE stream can tell clients to resync. That signal is still needed and still meaningful even with persistence - a MockServer reset doesn't reset `mock-ui`'s own SQLite history, so the reset-detection comparison moves to comparing the newly-fetched batch's shape against what `mock-ui` last saw *from MockServer specifically* (e.g. total MockServer-reported entries dropping to near-zero unexpectedly), not against the full accumulated persisted history, which by design no longer shrinks in step with MockServer's own log.
- **k8s storage: no PVC.** The SQLite files live on the pod's ephemeral filesystem (container writable layer, or an `emptyDir` if the container's default filesystem isn't writable) and are lost on pod restart/reschedule - this is intentional, not a gap: surviving a restart is explicitly not a goal (see Non-Goals), so there is nothing to keep durable across pod lifecycles. This also avoids the operational cost a PVC would add (provisioning, a new failure mode where PVC binding blocks `mock-ui` startup, storage-class dependency) for a benefit this change doesn't need. Local/docker-compose usage similarly needs no new mount - a plain local/ephemeral path is enough.
- **"No independent cache" requirement (`openspec/specs/mock-management-ui/spec.md`) needs no delta.** Its text is already scoped to "mock definitions" and CRUD actions ("every list, create, update, and delete action SHALL act directly and synchronously against the currently selected MockServer target's live expectation store") - request history was never in its literal scope. Prior designs avoided relying on that scoping and kept history non-persistent instead; this change relies on it explicitly for the first time. Called out here rather than left implicit, per the study's recommendation that this be a deliberate decision.

## Risks / Trade-offs

- [Durable accumulation trades "OOM from re-fetch/re-parse" (already fixed separately) for unbounded disk growth] → Mitigated by the fixed row-cap retention policy (Decisions above); accepted trade-off, not eliminated - disk is still finite and the cap is a config knob operators need to be aware of, not something enforced against actual available disk space.
- [SQLite writes happen on the same poller thread as the MockServer fetch, once per target per tick] → A slow disk could make a poll tick take longer, extending how long a target's snapshot lags MockServer under load. Accepted for POC scale; would need measurement if `REQUEST_STREAM_POLL_SECONDS` is lowered aggressively or target count grows large.
- [The `(timestamp, method, path, status)` dedup key can theoretically collide for two genuinely distinct concurrent requests] → Pre-existing, documented limitation carried over from pagination's current tie-break handling, not newly introduced (see Decisions above).
- [Default row cap (120,000/target) is sized against one reproduced load test, not measured real production traffic patterns] → Configurable via env var; flagged as worth revisiting after this ships, same posture the prior resilience change took toward its own per-tick fetch-cost trade-off.
- [History still does not survive a `mock-ui` restart or pod reschedule, since storage is local/ephemeral by design] → Accepted, explicitly out of scope (see Non-Goals) - this change targets in-process reliability (no silent loss to MockServer's own eviction) while `mock-ui` is running, not durability across restarts. A future change could add a PVC if restart-survival becomes a requirement.

## Migration Plan

- New `mock-ui` deployments: SQLite files are created on first poll tick; no migration needed.
- Existing deployments: no historical data exists in the old in-memory-only design to migrate forward - the SQLite store starts empty and begins accumulating from the first poll tick after this change is deployed, and starts empty again on every subsequent restart, same as today's in-memory behavior. This is a one-time, expected gap (nothing in the old design retained history across a deploy anyway), not a regression.
- Rollback: reverting to the prior in-memory-only version simply stops reading/writing the SQLite files; no data format to reverse-migrate since nothing downstream depends on the SQLite schema surviving a rollback.
